Der ssh.runpod.io-Basis-Proxy kann außerdem nur interaktive Terminals — kein Exec, kein scp, keine Tunnel.

### Nachtrag (Abend) — Tag-1-Ziel erreicht

- **Gebaut:** Alten Pod ersetzt: `llm-lab-a5000` (A5000, runpod/pytorch-Image, TCP 22 + HTTP 8000/8888, 50-GB-Volume) per RunPod-API provisioniert. Auf dem Pod (manuell, per SSH): venv auf `/workspace` (16 GB, restart-fest), `pip install vllm` (0.26.0), Qwen3-8B (16 GB → HF-Cache auf Volume) via `start_vllm.sh` in tmux gestartet. Beweis: `/v1/models` antwortet durch den RunPod-Proxy mit API-Key-Auth.
- **Gelernt:** (1) Direktes TCP-SSH = Exec + Copy + Tunnel — der Proxy kann nur Terminal. (2) RunPod schreibt Docker-Env nach `/etc/rp_environment`, gesourct nur in interaktiven Shells — Startskripte müssen Env defensiv selbst setzen. (3) vLLM-Speicherbilanz auf 24 GB: 15,27 GiB Gewichte + 1,19 Aktivierung + 0,58 CUDA-Graphs → 5,84 GiB KV-Cache-Pool = das Parallelitätsbudget für morgen. (4) Netzwerk-Volume (MooseFS): langsame Installation/Kalt-Imports, dafür überlebt alles Stop/Start. (5) Appliance-Image (vllm-openai) passt zu K8s mit `kubectl exec`; auf nacktem Pod braucht man Workstation-Image + eigene Prozessverwaltung (tmux).

## Di 28.07.2026 — Benchmark-Tag (+ ungeplante Migration)

- **Gebaut:** Lab nach EU-CZ-1 migriert: Network Volume `llm-lab-volume` (50 GB, überlebt jetzt sogar Pod-Terminierung) + RTX 3090. venv + vLLM 0.26 neu aufgebaut, `sweep.sh`-Harness geschrieben, kompletter Concurrency-Sweep 1→32 gefahren (0 Fehler), Ergebnisse (6× JSON + 6× GPU-CSV) im Repo.
- **Gelernt:** (1) Ein gestoppter Pod reserviert keine GPU — morgens war der A5000-Host belegt, 3 Startversuche vergeblich; Kapazität ist ein Betriebsrisiko. (2) Pod-Volumes kleben am Host, Network Volumes sind die Antwort — aber DC-gebunden und nur Secure Cloud; CA-MTL-1 konnte keine → Umzug nach EU-CZ-1 mit GPU-Wechsel A5000→3090 (gleiche Ampere-Klasse). (3) Benchmark-Design: nur EINE Variable ändern (Concurrency), Prompt-Längen fixieren, auf localhost messen, Perzentile statt Mittelwert. (4) Messergebnis: Batching ist bis c=8 fast gratis (48→338 tok/s bei ~150 ms TTFT), der Knick kommt bei c=16 (TTFT-Median ×7 auf 1,1 s), bei c=32 ist P99-TTFT 3,6 s. (5) Regel etabliert: Alles, was länger läuft als ein Kaffee, läuft in tmux.
- **Schiefgegangen:** Deploy-Review fing zwei stille Fehler (Port 8000 fehlte, HF_HOME/VLLM_API_KEY fehlten — Modell wäre auf der Wegwerf-Disk gelandet). SSH-Disconnect während pip — Installation überlebte, aber nur mit Glück; siehe tmux-Regel. TCP-Ports wechseln bei jedem Container-Restart.

## Do 30.07.2026 — Gateway-Tag

- **Gebaut:** LiteLLM-Gateway + Postgres via Docker Compose (healthcheck-gesteuerte Startreihenfolge). Virtuelle Keys für zwei Fakultäten mit Budgets ($5/$1 pro 30 Tage) und Rate-Limits (rpm 30/3). Rate-Limiting bewiesen (429 ab Request 4). Chargeback: eigene Token-Preise aus dem Capacity Model ($0,10/$0,41 pro Mio) in config.yaml — erster abgerechneter Request: $0,0000844, nachgerechnet exakt. Pod-Neuaufbau komplett per REST-API (MCP kann networkVolumeId nicht — getestet, bewiesen, Ebene tiefer gegangen). Volume-Konzept zahlte sich aus: venv + Modell überlebten den Pod-Wechsel, null Neuinstallation.
- **Gelernt:** (1) Config-Trennung: config.yaml = Struktur (Git), .env = Umgebung/Secrets (nie Git); Env-Variablen werden beim Container-ERSTELLEN eingefroren → --force-recreate statt restart. (2) Drei Key-Schichten: Backend-Key (Gateway↔vLLM), Master-Key (Admin), virtuelle Keys (Nutzer mit Budget). (3) Zwei Arten von 429: Nutzer-Quota vs. Backend-Cooldown (Circuit Breaker) — verschiedene Gegenmaßnahmen. (4) Abrechnung ist batch-verzögert (eventual consistency). (5) Thinking-Modelle verbrauchen max_tokens fürs Denken — finish_reason=length ohne Antwort. (6) UI/MCP/SDK sind Hüllen um dieselbe REST-API.
- **Schiefgegangen:** MCP-create-pod reichte networkVolumeId stillschweigend als Env-Var durch (mounts leer) — stille Parameter-Verluste sind gefährlich, immer das Ergebnis verifizieren. PowerShell zerhackt JSON-Escapes an curl.exe → Body immer als Datei übergeben (-d "@datei").

## Fr 31.07.2026 — Fallback-Tag (8 Fehler, 1 Triumph)

- **Gebaut:** Fallback-Modell Qwen3-0.6B auf :8002 (nach 1.7B-Fehlversuchen), Fallback-Kette `qwen-8b → qwen-mini` im Gateway, kompletter Failover-Zyklus live bewiesen: Normalbetrieb → Kill → automatische Fallback-Antwort (model-Feld: Qwen3-0.6B) → Recovery → stabile Ko-Residenz beider Modelle (3,7 + 19,8 GB). governance.md mit allen Belegen. Pod-Neuaufbau komplett per REST-API inkl. Port-Nachrüstung (8002).
- **Gelernt:** Acht Betriebsfehler an einem Tag, jeder mit Regel (Details in lernstoff/tag-5.md): KV-Mindestbedarf, belegte Ports (`ss -tlnp`), wechselnde TCP-Mappings, UTF-16-Falle, SIGHUP-Tod außerhalb tmux (2×), tmux-Präfix-Matching (`-t =name`), Speicher-Race bei parallelem Start, Readiness (bootender Dienst = toter Dienst). Ko-Residenz-Rezept: klein zuerst, groß danach; Fraktionssumme ≤ 0,93; 8B-Fußabdruck variiert ±1,5 GiB zwischen Boots.
- **Schiefgegangen:** Siehe „Gelernt" — der ganze Tag war produktives Schiefgehen. Kernerkenntnis fürs Konzeptpapier: Verfügbarkeit ist kein Feature, sondern Disziplin auf jeder Schicht (Prozess-Supervision, Readiness, Monitoring), und genau dafür existieren Orchestratoren wie Kubernetes/OpenShift.

## Sa 01.08.2026 — Monitoring-Tag (das System meldet sich zum ersten Mal selbst)

- **Gebaut:** Prometheus + Grafana als Compose-Services (Dashboard & Alerts als Code im Git, provisioniert statt geklickt), `gpu_exporter.py` (~40 Zeilen stdlib, nvidia-smi → Prometheus-Format auf :8888), 9-Panel-Dashboard (TTFT-P99, Durchsatz, Kosten/1k Tokens live, KV-Füllstand, Running/Waiting, GPU Compute vs. VRAM), 2 Alert-Regeln, docs/slo.md + docs/runbook.md. Härtetest: c=32-Lastlauf gegen das ko-residente 8B → `TTFTP99AboveSLO` feuerte planmäßig.
- **Gelernt:** (1) Pull macht Abwesenheit messbar — die `up`-Metrik erzeugt Prometheus selbst, ein toter Dienst kann sie nicht fälschen; Antwort auf den lautlosen Tod von Tag 5. (2) `for: 2m` = Entprellung: Alert-Müdigkeit ist gefährlicher als 2 Minuten Verzögerung. (3) Überlast trifft die Wartenden, nicht die Laufenden: TTFT P99 18,1s bei TPOT P99 73ms — vLLM schützt aktive Requests, die Queue leidet. (4) Kosten/Token sind blind für Qualität: der überlastete Lauf traf exakt den Capacity-Model-Preis ($0,42/M) bei fünffach gerissenem SLO. (5) Ko-Residenz end-to-end beziffert: 772→334 tok/s bei c=32. (6) Struktur/Secret-Trennung zum dritten Mal: prometheus.yml (Git) vs. pod-targets.json + Key-Datei (gitignored, File SD / credentials_file).
- **Schiefgegangen:** LiteLLM-Target 401 (schützt /metrics mit API-Auth, vLLM nicht — gelöst per `credentials_file`); zwei Panels „No data", weil vLLMs V1-Engine Metriken umbenannt hat (`kv_cache_usage_perc`, `inter_token_latency_seconds`) — Dashboards gegen die echte /metrics-Ausgabe verifizieren, nicht gegen Doku.
